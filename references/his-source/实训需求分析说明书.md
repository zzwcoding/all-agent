## 1. 业务背景

### 1.1 行业背景

随着医疗信息化建设的深入推进，各级医院已普遍部署了医院信息系统（HIS, Hospital Information System），实现了挂号、就诊、处方、收费、药品管理等核心业务的数字化。然而，业务系统的运行积累了海量数据之后，如何从这些数据中提取有价值的信息，为医院管理层提供决策支持，成为了一个新的挑战。

传统 HIS 系统侧重于业务流程的"在线事务处理"（OLTP），数据报表功能往往局限于简单的统计查询，难以支撑多维度的深度分析和可视化展示。医院管理者亟需一套能够覆盖门诊运营、财务结算、药事管理、疾病分析、患者画像等多个维度的数据报表与决策支持平台。

### 1.2 业务域概述

本项目以某医院的 HIS 业务数据为基础，覆盖以下核心业务域：

| 业务域 | 核心业务表 | 业务描述 |
|--------|-----------|---------|
| **挂号管理** | `register` (114条) | 患者挂号登记，是连接患者、科室、医生的枢纽数据 |
| **病历管理** | `medical_record` (104条) | 门诊病历，包含主诉、现病史、既往史、过敏史、体格检查 |
| **疾病诊断** | `medical_record_disease` (106条), `disease` (29,496条) | ICD-10 国际疾病分类标准，记录诊断信息 |
| **处方管理** | `prescription` (116条) | 医生开具的药品处方，包含药品、数量、用法 |
| **药品管理** | `drug_info` (3,066条) | 药品字典，包含药品名称、剂型、生产厂家、价格 |
| **检验检查** | `inspection_request` (101条) | 检验/检查申请单，记录项目、状态、费用 |
| **医技项目** | `medical_technology` (3,521条) | 医技服务项目字典和定价 |
| **组织机构** | `department` (240条), `employee` (145条) | 科室和医生/员工基础信息 |

### 1.3 业务流程说明

典型患者就诊全流程如下：

```
患者到院
  │
  ▼
挂号登记 ──────────────────────────────────────┐
  │ (register: 生成 case_number, 关联科室/医生)   │
  ▼                                              │
候诊等待                                          │
  │                                              │
  ▼                                              │
医生接诊                                          │
  ├── 问诊：书写病历 (medical_record)              │
  ├── 诊断：开具诊断 (medical_record_disease)      │
  │        关联 ICD-10 标准疾病编码 (disease)       │
  ├── 开药：开具处方 (prescription)                │
  │        选择药品 (drug_info)                    │
  └── 检查：开具检验申请 (inspection_request)      │
        选择医技项目 (medical_technology)           │
  │                                              │
  ▼                                              │
收费结算 ──────────────────────────────────────┘
  │ (按支付方式：现金/银行卡/微信/支付宝/医保卡)
  ▼
取药 / 做检查
  │
  ▼
就诊结束 (或退号/退费)
```

## 2. 业务痛点与需求分析

### 2.1 业务痛点

| 序号 | 痛点描述 | 业务影响 |
|------|---------|---------|
| **P1** | 医院管理层缺乏全局视角的运营仪表盘，每日关键指标（挂号量、收入、退号率）无法一目了然 | 管理决策滞后，无法及时发现运营异常 |
| **P2** | 各科室的接诊量、退号率、均次费用缺乏横向对比，资源分配无数据支撑 | 高负荷科室人员不足，低效科室资源浪费 |
| **P3** | 医生工作量没有量化排名，绩效考核缺乏客观依据 | 影响医生积极性和科室人员调度 |
| **P4** | 收费结算数据分散在多个系统中，支付方式占比、收入趋势无法实时掌握 | 财务分析效率低下，资金管理粗放 |
| **P5** | 药品销售缺乏 TOP 排名分析，库存管理凭经验而非数据 | 畅销药缺货、滞销药积压 |
| **P6** | 处方退药退费率缺乏系统监控，药事质量无量化指标 | 无法针对性改进处方质量 |
| **P7** | 疾病谱分布（ICD-10 章节）缺乏统计，公卫决策无数据支撑 | 疾病预防和健康教育缺乏方向 |
| **P8** | 病历书写完整率缺乏量化考核，医疗质量难以评估 | 潜在的医疗纠纷风险 |
| **P9** | 患者年龄结构、地域来源、复诊率等画像缺失 | 医院市场定位和服务优化无依据 |

### 2.2 核心需求

基于以上痛点，提炼出以下核心业务需求：

1. **院长驾驶舱**：一屏掌握全院运营核心 KPI（挂号人次、收入、处方数、退号率、疾病种数），支持近 7 日趋势查看和支付方式分布分析
2. **门诊运营分析**：科室/医生维度的接诊量排行、退号率监控、就诊状态流转分析
3. **收费与结算分析**：收入趋势、支付方式占比、各科室均次费用对比
4. **药品处方分析**：药品销售额 TOP20、药品类型占比（西药/中成药/中草药）、退药退费率趋势
5. **疾病诊断分析**：高频诊断疾病排行、ICD-10 章节分布、病历完整率五维度雷达评估
6. **患者画像分析**：年龄-性别金字塔、地域来源分布、复诊率统计

## 3. 大数据应用场景

### 3.1 场景全景图

### 3.2 场景一：HIS 业务数据离线批量同步（DataX → HDFS）

**业务背景**：HIS 系统每日产生大量业务数据（挂号、处方、病历等），需要将其从关系型数据库（MySQL）批量同步到大数据存储平台（HDFS），为后续分析做准备。

**技术方案**：使用阿里巴巴开源的 DataX 3.0 工具，将 MySQL 中的 15 张业务表全量导出为 CSV 格式，存储到 HDFS 的 `/data/xxx_mysql/` 目录。

**大数据知识点**：
- 异构数据源同步（MySQL → HDFS）
- 数据采集工具（DataX）的配置与使用
- 分布式文件系统（HDFS）的目录规划和文件管理
- 数据导入策略（全量 vs 增量）

**实训价值**：掌握企业级数据采集的标准流程，理解 DataX 的 Reader/Writer 插件架构。

### 3.3 场景二：Hive 数据仓库分层建模（ODS → DWD → DWS → ADS）

**业务背景**：原始业务数据不适合直接用于分析查询，需要经过清洗、标准化、维度建模、主题聚合等步骤，逐层加工为可直接查询的应用指标表。

**技术方案**：在 Hive 中建立四层数据仓库模型——

| 层级 | 数据库 | 定位 | 数据特征 |
|------|--------|------|---------|
| **ODS**（操作数据层） | `ods_db` | 贴源层，Hive 外部表直接映射 HDFS 原始 CSV | 原始格式，未做清洗 |
| **DWD**（明细数据层） | `dwd_db` | 数据清洗与标准化 | 维度退化、空值处理、字段拆分、编码标准化 |
| **DWS**（汇总数据层） | `dws_db` | 面向分析主题的轻度汇总 | 按天/科室/医生/药品/患者等维度聚合 |
| **ADS**（应用数据层） | `his_report_db` | 面向应用报表的指标表 | 7 张预聚合表，直接供 API 查询 |

**大数据知识点**：
- 数据仓库分层方法论（阿里巴巴 OneData 体系）
- Hive 外部表 vs 内部表的使用场景
- HiveQL 开发（JOIN、GROUP BY、CASE WHEN、窗口函数）
- 维度建模（星型模型/雪花模型）
- 分区表设计（按日期 `dt` 分区）

**实训价值**：通过实际业务数据完成完整的数仓分层设计，理解每一层的数据加工逻辑和业务含义。

### 3.4 场景三：Spark 离线计算引擎（ETL 加工）

**业务背景**：Hive 的 MapReduce 引擎在处理复杂多表关联和聚合计算时性能较低，需要引入 Spark 作为计算引擎，加速 ETL 加工过程。

**技术方案**：使用 Spark 3.3.3（Standalone + YARN 模式），通过 Spark SQL 或 DataFrame API 执行 ODS→DWD→DWS→ADS 各层的 ETL 计算任务。

**大数据知识点**：
- Spark 集群架构（Master/Worker、Driver/Executor）
- Spark SQL 与 Hive 的集成（共享 Metastore）
- DataFrame/Dataset API 编程
- RDD 的转换和行动操作
- Spark 任务调优（并行度、内存、序列化）

**实训价值**：掌握工业界主流的大数据计算引擎，理解 Spark 与 Hive 的协作模式，能够编写高效的 ETL 作业。

### 3.5 场景四：Kafka 实时消息队列（业务日志采集）

**业务背景**：除了离线批量的 T+1 数据处理，医院还需要对业务系统的操作日志进行实时采集和存储，用于异常监控、审计追溯和实时分析。

**技术方案**：搭建 3 节点 Kafka 集群，创建 `flume_kafka_topic`（3 分区 × 2 副本），模拟 HIS 业务系统产生 7 种类型的业务事件并发布到 Kafka。

**7 种业务事件类型**：

| 事件类型 | 权重 | 携带的关键数据 |
|---------|:----:|--------------|
| REGISTER（挂号） | 40% | 科室名、医生名、挂号费、支付方式 |
| PRESCRIPTION（开处方） | 25% | 药品名、药品类型、数量、金额 |
| INSPECTION（开检验） | 12% | 检验项目名、费用 |
| MEDICAL_RECORD（写病历） | 10% | 诊断名、ICD 编码 |
| DRUG_DISPENSE（发药） | 8% | 药品名、发药数量 |
| REFUND（退号） | 3% | 退号原因、退款金额 |
| PRESC_REFUND（退药退费） | 2% | 退药名称、退费金额 |

**大数据知识点**：
- Kafka 架构原理（Broker、Topic、Partition、Replica）
- 生产者 API（acks、压缩、批量发送）
- 消费者组模型与 Offset 管理
- 分区策略与 Leader 选举
- 副本机制与 ISR（In-Sync Replicas）

**实训价值**：深入理解分布式消息队列的核心概念，掌握 Producer/Consumer API 编程，理解 Kafka 在生产环境中的配置策略。

### 3.6 场景五：Flume 日志采集管道（Kafka → HDFS）

**业务背景**：Kafka 中积累的业务日志需要可靠地持久化到 HDFS 中，供后续的离线分析和数据回溯。

**技术方案**：部署 Flume Agent，配置 KafkaSource → MemoryChannel → HDFSSink 三级管道。Flume 作为消费者从 `flume_kafka_topic` 拉取消息，按日期分区写入 `/flume/flume/kafka/YYYYMMDD/`。

**大数据知识点**：
- Flume 架构（Source → Channel → Sink 三组件模型）
- KafkaSource 配置（topic、groupId、offset 策略）
- HDFSSink 配置（路径模板、文件滚动策略）
- Channel 类型选择（Memory Channel / File Channel）
- Flume 事务机制（at-least-once 语义）

**实训价值**：掌握大数据日志采集管道的搭建方法，理解 Flume+Kafka 组合方案在企业中的应用。

### 3.7 场景六：Hadoop 集群运维管理

**业务背景**：整个大数据平台运行在 3 节点 Hadoop 集群上，需要掌握集群的安装部署、配置管理和日常运维。

**技术方案**：3 台 CentOS Stream 9 虚拟机组成 Hadoop HA 集群。

| 节点 | IP | 角色 |
|------|-----|------|
| master | 192.168.100.200 | NameNode, ResourceManager, MySQL, Hive, ZooKeeper, Kafka Broker#0, Flume, Spark Master |
| slave1 | 192.168.100.201 | DataNode, NodeManager, Kafka Broker#1, Spark Worker |
| slave2 | 192.168.100.202 | DataNode, NodeManager, Kafka Broker#2, Spark Worker |

**大数据知识点**：
- Hadoop 核心组件（HDFS + YARN + MapReduce）
- HDFS 读写流程（NameNode 元数据管理，DataNode 块存储）
- SSH 免密登录配置
- 集群配置文件管理（core-site.xml, hdfs-site.xml, yarn-site.xml）
- Shell 运维脚本编写（一键启停）
- Web UI 监控（HDFS:9870, YARN:8088, Spark:8080）

**实训价值**：从零搭建企业级 Hadoop 分布式集群，培养 Linux 系统管理和集群运维能力。

### 3.8 场景七：双数据源报表 API 服务（Spring Boot）

**业务背景**：经过大数据平台处理后的指标数据存储在 MySQL `his_report_db` 中，需要开发 REST API 服务供前端消费。同时，部分实时性要求较高的查询需要直接访问 HIS 源库。

**技术方案**：使用 Spring Boot 3.3.5 + MyBatis-Plus 3.5.10 构建后端服务，通过 `dynamic-datasource` 实现双数据源路由：
- **主数据源** `his-report`：查询 ADS 预聚合表（7 张 ads_* 表），11 个接口
- **辅数据源** `his`：查询 HIS 源库进行实时统计（register, medical_record, disease），7 个接口

提供 18 个 REST API，统一返回 `{code: 200, message: "success", data: {...}}` 格式。

**大数据知识点**：
- 大数据分析结果如何服务于业务系统（ADS 表设计）
- 多数据源架构在报表系统中的应用
- ORM 框架与大数据结果表的配合

**实训价值**：补齐全链路从数据处理到 API 服务的环节，掌握数据服务层的开发。

### 3.9 场景八：多维度可视化数据分析（Vue + ECharts）

**业务背景**：分析指标需要通过可视化图表呈现给医院管理层，使其能够直观、快速地理解数据并做出决策。

**技术方案**：Vue 2.7 + Element UI + ECharts 5.5，构建 6 大分析主题页面，使用 9 种图表类型，共 21+ 个图表实例。

| 页面 | 使用图表 |
|------|---------|
| 院长驾驶舱 | KPI 卡片、双 Y 轴折线图、环形图、横向柱状图、预警列表 |
| 门诊运营分析 | KPI 卡片、横向柱状图、柱状图、漏斗图、数据表格 |
| 收费与结算分析 | KPI 卡片、面积图、环形图、横向柱状图+均值线、数据表格 |
| 药品处方分析 | KPI 卡片、横向柱状图(按类型分色)、矩形树图、折线图+均值线、数据表格 |
| 疾病诊断分析 | KPI 卡片、横向柱状图、矩形树图(按 ICD 章节)、雷达图(五维度)、数据表格 |
| 患者画像分析 | KPI 卡片、双向柱状图(人口金字塔)、柱状图、统计卡片 |

**大数据知识点**：
- 大数据可视化最佳实践（图表选型与业务场景匹配）
- 前后端分离架构（API 代理、跨域处理）
- 大屏设计 Token 体系（品牌色、间距、字体、动画）
- ECharts 图表配置与自适应

**实训价值**：掌握大数据全链路的最后一环——数据可视化，理解从数据到洞察的完整价值链。

## 4. 实训目标

### 4.1 知识目标

1. 理解医院信息系统的业务模型和数据模型，掌握 HIS 核心业务流程
2. 理解大数据技术栈的体系架构及各组件的协作关系
3. 掌握 Hadoop 生态体系（HDFS、YARN、Hive、Spark、Kafka、Flume）的核心原理
4. 掌握数据仓库分层建模方法论（ODS → DWD → DWS → ADS）
5. 理解实时流处理与离线批处理的 Lambda 架构思想
6. 掌握 Spring Boot + Vue 全栈开发的基础知识
