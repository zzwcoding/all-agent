# 信号归一指南（proposal-pool · 全文域无关）

把「发生了什么」变成「提议改什么、依据什么、等谁裁决」。本指南是 SKILL.md 工序
第 1–2 步的细则：五类信号的受理标准、证据等级、逐字段归一操作。域知识一律不入
本文——域语义只存在于信号素材与本体仓里。

## §1 信号是什么、什么算一条合格信号

业务语义循环的三源信号：

| 源 | 指什么 | 典型载体 |
|---|---|---|
| 监督 | 自动巡检/闸对仓内数据的业务面告警 | 巡检报告、闸输出、告警摘录 |
| 自检 | 建造工序自己留下的疑点与「待 Owner 确认」标注 | 草案疑点清单、走查遗留 |
| 交互 | 用户在对话里明说的口径、裁决、纠错 | 对话原文（须先转录落盘） |

一条**合格信号**必须同时满足三条，缺一退回补充、不做猜测补全：

1. **可定位**：说得出何时、何载体、原文在哪（可引用到文件/记录）；
2. **可证伪**：说得出期望与实际的差别（哪两个数字/口径/行为对不上）；
3. **可裁决**：Owner 凭它能做判断（yes/no 或二选一），不需要再脑补业务背景。

不合格信号的处理：逐条给退回原因（缺哪条、补什么），**不静默吞掉**；部分可用的
拆分受理，不硬凑成一条提案。

## §2 五类信号的受理标准（source-signal.kind 对号入座）

| kind | 定义 | 受理门槛 | 不受理 / 降级情形 |
|---|---|---|---|
| 拒答 | 运行时语义服务按「仓内没有」拒答的记录 | 拒答话术带「缺什么」分层说明；确认所缺概念本应可答（不属面外） | 面外问题（不属本体语义面）不受理；同一概念重复拒答合并为一条 |
| 疑点 | 工序标注「待 Owner 确认」的脏特征/推断残留 | 有位置（文件+元素）+ 输入原文证据 | 已有 open 提案同标的疑点不再单开——转冲突预检登记 |
| 对账缺口 | 报表/指标与事实源对不上 | 双方都可引证（哪张表/哪个元素/哪个字段，各是什么值） | 无数值纯感受性抱怨退回 |
| 监督 | 值域越界、枚举外取值、双值行等业务面告警 | 告警可复现（规则+样本各是什么） | 工程面告警（脚本/闸/安装位坏了）不进提案池——那走工程错路由，不属业务语义 |
| 交互 | 用户明说的口径/裁决/纠错 | 对话原文已转录落盘成仓内文件 | 转述第三方口径且无出处 → 降级为疑点受理 |

一提案一**主信号**（kind/ref 只填主信号）；附带信号写进正文证据展开，不硬塞进头。

## §3 证据等级与标注（source-signal.ref 落什么）

| 等级 | 是什么 | 要求 |
|---|---|---|
| A | 仓内机读文件锚点（模型 YAML/注册表/机读表） | 路径+#锚点直指元素或键 |
| B | 仓内人读文档（走查记录、报告） | 路径+#小节名 |
| C | 仓外材料（对话原文、外部文档、截图内容） | **先全文转录落盘成仓内文件**才算证据；转录件头部注明「转录自仓外」与出处可溯描述 |

规则：

- 每条提案至少一条证据，`source-signal.ref` 指向主证据，其余证据在正文展开；
- rationale 是一段话的「为什么」，证据文件是可回查的「凭据」，两者不互相替代；
- 只有 C 级证据的提案先落 `status: draft`，证据升级为 A/B 后才翻 open——仓外
  之言不可直接驱动 open 提案；
- 证据路径解析规则（仓根相对优先、#锚点容许、绝对路径拒收）见仓根共享规约
  proposal-format.md §5，与检查工具行为一字不差。

## §4 逐字段归一操作细则

- **id**：域段取靶元素归属的域目录名（照本体仓）；NNN 取池内同域最大号顺延——
  起号前先过一遍提案池现状（列现有 PROP 文件），不许凭记忆报号。
- **title**：一句话动宾结构，带靶 ID，让 Owner 不点开正文也知道要动什么。
- **source-signal.kind / ref**：按 §2 定类，按 §3 定证据。
- **target.model**：靶元素 ID 前缀在本体仓 schema 依赖白名单 idPrefixes 里登记的
  模型标识；查不到登记 = 这个 ID 本身可疑，先回 §2 查信号，不硬填。
- **target.element**：优先信号里显式给的 ID；只有名称时先在真域解析出唯一 ID
  （命中多个或零个都退回补充，不靠名称猜），把解析依据写进正文。
- **change**：以真域为准，不许凭印象——靶不存在 → add；存在且方向是补/改 →
  modify；存在且方向是停用/废弃 → deprecate。归一后仍报「已存在/不存在」的，
  按检查工具的报错回改，不改工具口径。
- **rationale**：一段话说清「什么信号 → 什么缺口 → 建议什么动作 → 待谁裁决什么」。
- **正文**：两节起步——「草案内容」（拟新增/拟修改的元素 YAML 或要点，标注
  「进仓走 MR，非已定稿本体」）与「证据展开」（逐条列证据与信号原文摘录）。

## §5 查重与冲突预检（工序第 3 步的处置细则）

- 落盘前必跑检查工具（确定性四类：schema 字段/枚举、target 存在性、同靶冲突、
  证据在档）；四类全过才算起草完成。
- 报 `proposal-conflict` 的处置：**不撤旧提案、不改旧提案**；新提案标 draft，
  正文登记「与谁（哪份 PROP）、因什么矛盾」；两份 open 提案谁对，是 Owner 的
  裁决点，skill 不替人取舍。
- `add` 报「已存在」= 信号过时或 change 选错：先复查真域现状，再按 §4 重定
  change，不许绕过检查硬提。
- 同靶同 change 的重复提案闸不判（机械面只报方向矛盾）：起草前先过池查重，
  相同提议并入既有提案的正文附议，不另开新号。

## §6 状态流转纪律（工序第 4 步的处置细则）

- `draft`：起草中 / 证据只有 C 级 / 有未解冲突。draft 提案在池内但不算待决。
- `open`：自检全过、证据 A/B 级、无未解冲突，等待 Owner 裁决。
- `accepted` / `rejected`：**只由 Owner 裁决产生**；skill 只代执行翻转——改
  status 一处 + 正文留裁决注记（日期、裁决出处/一句话理由），不删档不改其他字段。
- `rejected` 提案是资产：同一信号再现时先查池，被拒过的提议不重复起草；确要
  翻案，新开提案并在正文引用旧号与翻案理由。
- 池现状问答（「查提案池状态」）：按 status 分组报数 + 未解冲突清单，裁决排期
  由人定，skill 不催裁不代裁。
