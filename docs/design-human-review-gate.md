状态: 已过目裁决（2026-09-20 Owner 裁决：§6 七点全按推荐，见 §8；ADR 0003 随施工票落盘）

## 0. 一句话结论

推荐 **"审记旁档状态机 + 哈希锚定"（选型 A 吸收 C 的防伪面）**：生成物本体一字不动（`--check` 防陈旧与归档闸契约零破坏），人审结论落旁档审记文件，审记锚定"被审版本的内容哈希+commit"——本体再生即哈希变、已审状态自动失效回落待人审；按置信度三档分级放开（纯机读派生物免审、骨架型首审+变更审、宽输入型全审），打回统一走既有信号路由表。

## 1. 现状盘点：三生成物的人审头、审者、审什么

### 1.1 三处现状（实查注源）

| 生成物 | 人审头现状 | 机判锚 | 差异 |
|---|---|---|---|
| 开发包 `exports/devkit/bohai/devkit.md` | 正文头部 `status: 待Owner人审（生成物禁手改，可再生）`（tools/app_pack_gen.py 写死字面） | specs/archive-registry.json devkit 类：`status` 唯一合法值即上串，`flippedBy: 不适用（…人审结论经提案/票据落定后随再生更新）` | — |
| 技能包 `exports/skillpkg/bohai/SKILL.md` | frontmatter + 正文**双处**同款 status 行（tools/skill_pack_gen.py） | skillpack 类：同 devkit，单值钉死 | — |
| MCP 清单 `exports/mcp/capability-manifest.json` | `"status": "已生成"`——**没有人审态** | mcp-manifest 类：`values: ["已生成"]`，`flippedBy: 不适用` | **三处不一致：manifest 根本不在人审头体系内**（票 37 只登记了 devkit/skillpack 两类） |

### 1.2 三个关键实证（本设计的出发点）

1. **状态字段被闸钉死为不可翻转**：归档闸契约明文 `flippedBy: 不适用`——"待Owner人审"不是审批流的起点态，而是一句**永久性声明**；没有任何机制、任何人能把某个生成物的 status 翻成"已审"。这正是 §6.5 #3"状态标记，非审批流"的机判实证。
2. **审者与时点**：PRD 决策 1 = 单人仓（仓主即 Owner，"MR 人审由仓主在 Git 完成"）；决策 2 = 发布前过一道人确认。本仓无独立发布步（MCP 发布 = exports 在库，docs/mcp-server.md），所以"发布前"事实落位为**入库/再生时点**——即每次生成器驱动再生后，那道"人确认"该发生而无处落笔。
3. **审什么**：二期收官报告 §5 #4 定调"人审的是**内容**不是格式"——格式面已由三重机判包死（`--check` 逐字节防陈旧 + 归档闸必备字段 + 生成器确定性装配零 LLM 零时间戳）。人审对象 = **派生物对本体的转译保真度**（装配没漏、没串、没把开放提案内容装错位）。

### 1.3 现状的实质

承诺在场（status 行 + 禁手改声明 + 归档闸机判），**履约载体缺失**（无审记落点、无状态流转、无"谁在哪天认可了哪个版本"的痕迹）。本设计要补的是载体，不是承诺。

### 1.4 现行机判面地图（人审闸只能建在这些闸之上，不能与它们重叠）

| 闸 | 管什么 | 管不到什么 |
|---|---|---|
| 生成器确定性装配 | 零 LLM 零时间戳，同输入同输出（二期收官报告 §3） | 输入本身错（本体内容错、开放提案内容错）——装配忠实于错输入 |
| `--check` 防陈旧（回归底线第七条，三生成物各一条命令） | 入库副本 = 再生结果（版本不漂） | 再生结果本身对不对——它保证"没被手改"，不保证"该被审过" |
| 归档闸（specs/archive-registry.json） | 产物类在场、必备字段在场、status 合法值在场 | status 之外的一切内容；以及"待Owner人审"承诺是否真的被人履行过 |

三闸合围后的真空恰好一个格子：**"这版生成物被人看过并认可过"没有任何机判或人审载体**。人审闸设计 = 只填这个格子，不重复三闸任何一个的判定。

## 2. 承载形态三选型对比

### 2.1 三选型

| 维度 | A. 状态机文件制（审记旁档） | B. Git MR 制（生成物改动必经 MR） | C. 签名制（Owner 对哈希签名落档） |
|---|---|---|---|
| 摩擦 | 低：纯仓内 JSON/MD + 一个校验脚本，随再生一个动作 | 高：单人仓给自己开 MR；生成物再生由票驱动，提交碎、MR 频度与票频度耦合 | 中：每次再生后需重签一次，签名工具链要维护 |
| 可追溯性 | 中→强（若做哈希锚定，见 2.3）：审记记 commit+哈希，git 可回溯 | 强（git 原生 log/blame） | 强（防篡改硬保证） |
| 防伪/失效能力 | 取决于是否锚定哈希（A 裸做只防"没审"，不防"审的是旧版"） | 中：merge 保证内容合入，但不自动检测"审后再生" | 强：哈希不匹配签名即失效 |
| 与 `--check` 的张力 | **零张力**（旁档不碰本体） | 低张力（MR 合的就是再生结果）但流程冗余 | 零张力（签名旁档） |
| 与归档闸 status 契约的张力 | **零**（不动 status 字段） | 需要改 status 语义或引新字段 → 动闸 | 零 |
| 单人场景的实质效用 | 高：审记 = 认可留痕 + 失效自动检测 | 低：自审自合，MR 形态仪式大于实质（PRD 决策 1 先例：MR 人审=仓主自己在 Git 完成，本体已如此，派生物再来一遍是双倍仪式） | 中：自签自认防的是"遗忘/错认版本"，不是"他人篡改" |
| 与"skill+脚本，不建代码系统"形态的契合 | 高（一个脚本+一个登记文件） | 中（引入分支/合并节奏到派生物面） | 低（GPG/密钥管理超出仓形态） |

### 2.2 核心冲突：`--check` 防陈旧 vs 人审改动内容

**冲突陈述**：`--check` 的语义是"入库副本 = 现场再生结果，逐字节一致"（tools/app_pack_gen.py 头注 L35–43；skillpack/manifest 同款手法，二期收官报告 §2 第七条底线 + §5 #3"派生物禁手改的机械面"）。而传统审批流的产出物是**对文件内容的修改**（批注、修订、直接改字）。若人审以"改生成物"为产出，逐字节比对必红——人审与防陈旧在同一个字节串上是**互斥操作**。归档闸把这一冲突制度化成了现状：status 单值钉死 + flippedBy 不适用，等于宣布"生成物本体在人审面前也是只读的"。

**解法（三选型共同的前提，也是本设计的枢纽）**：

> **人审的产出不是修订，而是"审定批注"旁档；内容修正诉求一律回流真源。**

- 审定批注 = 独立审记文件（认可意见、审点清单、驳回理由），永不写回生成物本体。
- 内容有错 → 错在真源：本体内容错走**提案池 MR**（F13 流程，业务语义循环），生成器装配错走 **tickets/ 票**（工程错道）——修完真源 → 再生 → 生成物自然更新。
- 这与现状完全自洽：生成物头部早已声明"生成物禁手改，可再生"（三处 status 串自带），归档闸早已宣布"人审结论经提案/票据落定后随再生更新"（specs/archive-registry.json flippedBy 原文）——**现行契约其实已经规定了"旁档回流"解法，缺的只是旁档本体**。

### 2.3 推荐：A 为骨架 + 吸收 C 的哈希锚定；B 不采用

- **A 为骨架**：每类生成物一份审记旁档（建议 `exports/reviews/<生成物>-review.json`，逐版本追加不覆盖），字段最小集：`{target, reviewedCommit, reviewedSha256, verdict(已审/打回), checkpoints[], notes, reviewedBy, date}`。归档闸登记新产物类 review-record（照票 37 给 devkit/skillpack 登记的先例，反向把审记本身入闸）。
- **吸收 C 的哈希锚定（推荐的关键一步）**：校验脚本在核对审记时**现算生成物 sha256 与 `reviewedSha256` 比对**——不一致（本体再生过）则已审结论**自动失效回落"待人审"**。这一步把 C 的防伪力嫁接进 A 的低摩擦骨架，且**复用了 `--check` 的既有哲学**（逐字节比对判"版本是否还作数"）：`--check` 判"入库=可再生"，哈希锚定判"已审=就是这一版"。两处比对同构，维护心智为一套。
- **B 不采用**的理由是结构性的：① 单人仓 MR 是自审自合（决策 1 已明示），形态仪式无实质增量；② 派生物禁手改 ⇒ MR 的 diff 恒等于再生结果 ⇒ MR 审阅退化为"看 diff 有没有"，这正是 `--check` 已经机判的事——MR 不产生新信息；③ 本体的内容人审已经在提案池 MR 流程里（F13），生成物再开 MR 会造成"两个 MR 面同审一份内容"的重复。B 的可追溯优点由 A+哈希锚定的 `reviewedCommit` 字段等价获得。

### 2.4 生命周期走查（推荐形态下一次完整的审-改-再审循环）

以"本体内容修正导致生成物再生"为最常见场景：

1. **待审**：生成物在场，审记无有效记录（或从未 init）——verify 报"待人审"。
2. **审**：Owner 读生成物（对照本体真源抽查装配保真度，§1.2 审什么），认可 → `approve` 写审记：verdict=已审 + 锚定当下 commit 与 sha256 + 审点清单（如"装配完整性/提案内容落位/约束节原样"）。
3. **真源变更**：本体提案合入 → 生成器再生 → 生成物字节变 → 归档闸 `--check` 绿（副本=再生结果，防陈旧闸永远绿，**它不受人审影响，这正是旁档设计的意义**）。
4. **自动失效**：下次 verify 现算 sha256 ≠ 审记锚定哈希 → 已审结论失效，状态回落"待人审"，留痕保留旧审记（追加不覆盖，历史可查）。
5. **再审**：Owner 只需对照 diff（git 可给再生 commit 与被审 commit 的差异）看变更节——若变更不触及上次审点，可在新审记里引用旧审记声明"仅增量审"（首审+变更审档的核心动作，§3.2）。

整个循环里生成物本体零手改、`--check` 零冲突、归档闸零改约——冲突（§2.2）在机制上不可发生，而非靠纪律避免。

## 3. 按置信度放开的分级建议（决策 2 的"按置信度放开"）

### 3.1 置信度判据（四条，域无关可复用）

1. **再生确定性**：零 LLM、零时间戳、逐字节可再生 → 确定性高（三生成物当前全满足，二期收官报告 §3"确定性装配"）。
2. **消费方是谁**：纯机读（消费方是程序，错内容会在下游校验处炸出来）vs 面向人（消费方是人，错话术直接误导且无下游兜底）。
3. **输入面宽度**：固定输入（出厂集固定件）vs 扫描开放输入（如 devkit 装配时扫描 docs/proposals 开放提案 frontmatter，tools/app_pack_gen.py"开放提案开关：启用"）——输入面越宽，装配错位面越大。
4. **变更频度与 diff 可读性**：再生频繁且 diff 人可读 → 审查边际成本低；diff 全是机械重排 → 全审价值低。

### 3.2 三档分级建议

| 档位 | 审查义务 | 判据组合 | 现三生成物落位建议 |
|---|---|---|---|
| **免审级**（抽查） | 不要求审记在场；批收官抽查 | 机读消费 + 下游硬闸兜底 + 固定/窄输入 | **manifest**：消费方是语义服务与 CI（capability-manifest 被 `--check` 与票 24 smoke 消费），错内容下游必炸；现状它本就没有人审头——把现状**明文化**为免审级并登记，消除"三类不一致" |
| **首审 + 变更审** | 首版全审落审记；此后再生仅当 diff 触及人审过的**内容节**才重审（哈希锚定自动检测版本变化，审记里可声明"只审 X 节"） | 面向人 + 结构骨架确定性 + diff 可读 | **skillpkg**：工序路由/问答卡是静态骨架文本（票 39 已常数化单一真源），变更集中于切片内容 |
| **全审级** | 每次再生后哈希失效即须重审，审记不在场 = 不得对外交付 | 面向人 + 宽输入（开放提案扫描） | **devkit**：装配面最宽（提案 frontmatter 扫描），且面向人无下游校验 |

- 分级的精神：**置信度放开 ≠ 免除声明**。免审级产物仍要在登记表里登记为"免审"——"有意不审"必须是显式决定而非遗漏（本仓纪律：明示去向不悬着）。
- 分级可随证据翻转：某免审级产物真在下游炸出内容错 → 升档走票（信号路由：工程错道）。

### 3.3 四判据怎么组合成档位（可操作的组合规则，域无关）

| 判据 | 问法 | 任一为"否"的效果 |
|---|---|---|
| 再生确定性 | 删掉生成物后能否逐字节重造？ | **封顶首审级**（不可免审——连再生都不可靠的产物无从谈置信度） |
| 消费方 | 主要消费方是程序且下游有硬闸？ | **封顶首审级**（面向人无兜底 → 不可免审） |
| 输入面 | 输入全部固定且经出厂集锁定？ | **封顶全审级**（扫开放输入 → 不可降为首审+变更审以下） |
| diff 可读性 | 再生 diff 人可读懂变更实质？ | 降一档义务（全审 → 首审+变更审；此时变更审改为"首审级抽检"） |

- 组合读法：先按前两判据取"最高允许档位"，再按后两判据向下修。三生成物落位（§3.2 表）即此规则的机械应用结果，非拍脑袋。
- 新产物接入（第二域、新生成器类型）时按同一张表判档——判档规则本身域无关，落档结果随产物性质走。

### 3.4 分级的两条边界情形（预先定规则，不留悬案）

1. **免审级产物在下游炸出内容错**：升档走票（工程错道）——升档前先修下游闸为什么没拦住（下游硬闸失效是免审级成立的前提，前提塌则档位塌）；修复票与升档票可并一案。
2. **审记丢失/损坏**：verify 按"待人审"处理（缺失 = 无效，宁多审一次不放过），不做审记重建——审记的权威来自"当时落笔"，重建出来的审记是伪造历史。此规则同时是免审级与全审级的公共底线：**审记可以缺，不可以编**。

## 4. 与提案池 MR 流程的一致性

- **两者都是人审，但审的对象与问题不同，形态不必统一为 MR**：
  - 提案池 MR（F13）：审**真源内容变更诉求**（本体该不该这么改）——业务裁决，PRD 决策 1"MR 由人完成"。
  - 人审闸：审**派生物转译保真度**（真源到派生物有没有走样）——验收性质。
- **需要统一的是三件事，不是形态**：
  1. **结论词汇统一**：提案池 open→accepted/rejected；人审闸 verdict 用同款二元（已审/打回），不自造第三套词。
  2. **留痕纪律统一**：都不以对话转述存活（协议第 7 条精神）——提案落 `docs/proposals/`，审记落 `exports/reviews/`，各有落盘真源。
  3. **打回路由统一**：人审打回不是死胡同，按 `policies/signal-routing.json` 分道——本体内容错→业务错道（提案池），装配/生成器错→工程错道（票）。人审闸因此成为信号路由表的一个**新信号源**（与元循环探针同位），而非独立流程孤岛。
- ADR 0002 先例佐证"形态不必统一"：本仓已裁决审查不走票内 MR/review 形态而走独立窗+落盘+整改闭环——**"人审 = 独立留痕 + 裁决落档"已是本仓验证过的人审范式**，人审闸照搬该范式即可，无需 MR 仪式。

### 4.1 两面人审对照表

| | 提案池 MR（F13） | 人审闸（本设计） |
|---|---|---|
| 审的对象 | 真源内容变更诉求（本体该不该改） | 派生物转译保真度（真源到派生物有没有走样） |
| 审的性质 | 业务裁决（Owner 裁决 open→accepted/rejected） | 验收确认（认可/打回） |
| 承载形态 | 提案文件 + MR 由人合 | 审记旁档 + 哈希锚定 |
| 打回去向 | rejected 存档，信号可再起 | 强制路由：业务错→提案池；工程错→票（§4 第 3 条） |
| 留痕落点 | docs/proposals/ | exports/reviews/（建议，决策点 4） |

两面在"本体内容错"处交接：人审闸打回 → 提案池起草 → MR 合入 → 再生 → 人审闸重审——**闭环经过两面而非在任一面内自闭环**，这是形态不必统一的根本原因：统一形态反而会让交接点模糊。

## 5. 明确不做与开放问题

### 明确不做

1. 不做在线审批 UI / 多人协作权限（PRD 决策 1 单人范围，留待真正多人时再议）。
2. 不做生成物手改白名单——"禁手改"不松动，任何情况下人审都不落笔于生成物本体（§2.2 枢纽结论）。
3. 不引入外部签名基础设施（GPG/密钥环）——哈希锚定在脚本内现算即可，C 的其余部分不移植。
4. 不把人审塞进 ci.sh 每提交硬闸——人审是节奏性动作（发布/收官时点），机判四闸才是每提交闸；两者节奏混排会把流水线卡死在等人。
5. 不动三生成物既有 status 行的字面（生成器字面、归档闸契约、`--check` 全依赖它）；"已审/失效"状态只活在审记旁档。

### 开放问题

1. **manifest 纳入与否**：本方案建议"纳入登记为免审级"（消除三类不一致），但"manifest 保持体制外"也是自洽选项——Owner 拍板。
2. **"已发布"要不要作为独立状态**：本仓无独立发布步；若未来出现真发布动作（对外交付 MCP 服务给第三方），审记需增 published 态与发布留痕——现在只预留字段不实现。
3. **审记的 reviewedBy 在单人仓怎么落**：git 身份即可还是要求显式声明——形式问题，施工票定。
4. **"首审+变更审"档的"只审 X 节"声明粒度**：节级（MD 标题）还是块级——skillpkg 施工时按实际 diff 形态定。
5. **新产物接入时的判档时机**：生成器票内判档（产物随票诞生即定档，推荐——票 35/36 先例是生成物与闸同票入库）还是产物入池后补判（多一道账）——施工票 2 时一并定入登记表维护纪律。

## 6. Owner 需拍板的决策点清单

> 每条附本方案倾向与理由，拍板只需对编号表态。

1. **承载形态**：A（审记旁档状态机+哈希锚定，推荐）/ B（MR 制）/ C（签名制）——推荐理由见 §2.3；若 Owner 认为未来会转多人协作，B 的论证需重开（多人时 MR 的防伪与分工价值才出现）。
2. **manifest 的档位**：纳入登记为免审级（推荐，消除三类不一致且"有意不审"显式化）/ 维持体制外 / 升为首审级。
3. **三生成物初始档位**：认可 §3.2 落位（manifest 免审 / skillpkg 首审+变更审 / devkit 全审）或调整——§3.3 组合规则是判档依据，调整请指明是改规则还是改例外。
4. **审记落点**：`exports/reviews/`（推荐：随产物走，归档闸新登记 review-record 类后天然入闸）/ `docs/meta/`（与体检留痕同域，但离产物远、归档闸覆盖不到 exports 语义）。
5. **失效严格度**：哈希不一致即自动失效（推荐：零宽限期，机制简单且宁可多审一次）/ 给 N 天补审宽限（引入时间参数，脚本复杂度与"宁多勿漏"精神相悖）。
6. **打回是否强制留痕**：硬性要求当场生成提案/票（推荐：照信号路由表"每条信号有去向"纪律，杜绝打回悬在审记意见里）/ 允许仅记审记意见。
7. **裁决落 ADR**：按 ADR 0002 同款形态落 ADR 0003（推荐：本裁决与 0002 同类——流程形态裁决，需生效范围与推翻条件；0002 的推翻条件句式可直接复用）/ 仅以本方案过目记录为准。

## 7. 施工拆票建议形状（裁决后拆，预计 2–3 张）

> 形状仅供参考；拆票按交接包自包含纪律补全 AC 表（续跑协议第 8 条：票面 AC 表为断言真源）。

- **票 1 · 审记格式与状态机脚本（脚本轨 TDD）**：`tools/review_gate.py` 四动作（init/approve/reject/verify）+ 哈希锚定校验（verify 现算 sha256，不一致即报失效）+ 退出码契约（0 一致/1 失效或缺失/2 配置错，照 --check 家族惯例）+ 出厂集 `fixtures/review-gate/` 正负变体（审记缺字段红/哈希不匹配红/verdict 非法值红/正常流转绿/失效后重审恢复绿）+ specs/archive-registry.json 登记 review-record 产物类（照票 37 先例：requiredFields 以实跑驱动收敛）。**验收核心 AC**：verify 对"生成物被再生"场景必须红（负变体钉死自动失效语义）。
- **票 2 · 三生成物接线与档位登记**：三生成物在登记表落档位（manifest 免审/其余按裁决）+ devkit/skillpack 生成器头部 status 行追加审记指针声明（**生成器字面变更 → 同票重 gen + `--check` 同步刷新**，这是本设计唯一合法触碰 exports 的路径——照票 35/36 生成物入库与闸同步先例）+ 批收官清单/回归底线增一条 verify 命令（软闸措辞：审记缺失或失效 = 收官清单挂账项，不阻塞四闸）。
- **票 3 · 文档对齐（小票）**：ADR 0003 落裁决（若决策点 7 选 ADR）+ PRD 决策 2 状态追认（"二期可按生成器置信度放开"→"已按三档分级落地，判档规则见设计案 §3.3"）+ CONTEXT.md 增「人审闸」词条 + 信号路由表增"人审打回"信号源条目（含实例指针：票 2 收官时的首个真实打回或免审登记即为实例）。

依赖关系：1 → 2 → 3 串行；票 2 必须在票 1 的格式冻结后动 exports（否则生成器声明的指针格式无真源）。
