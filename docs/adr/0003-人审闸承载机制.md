# ADR 0003 · 人审闸承载机制（审记旁档状态机 + 哈希锚定）

状态: 已采纳
日期: 2026-09-20
结论: 生成物人审闸采用「审记旁档状态机 + 哈希锚定」承载（选型 A 吸收 C 的防伪面）：人审结论落 `exports/reviews/` 审记旁档，逐版本追加不覆盖；verify 现算生成物 sha256 与审记锚定哈希比对，本体再生即哈希变、已审结论自动失效回落待人审，零宽限；按置信度三档分级放开（manifest 免审 / skillpkg 首审+变更审 / devkit 全审）；打回强制当场开单走信号路由表。生成物本体一字不动——人审的产出是审定批注，不是修订。
底图: docs/design-human-review-gate.md §8（Owner 裁决记录 2026-09-20，§6 决策点七点全按推荐）；票 45（tools/review_gate.py 审记状态机落地）与票 46（三生成物接线与档位登记 + 首审基线 exports/reviews/devkit-review.json、SKILL-review.json）为实弹证据。
遗留: published 态只预留字段不实现（§8 开放问题②随票定——本仓无独立发布步，未来出现真发布动作时审记再增 published 态与发布留痕）。

## 背景

PRD 决策 2：「生成器产出人审闸：设——开发包/MCP 发布前过一道人确认；二期可按生成器置信度放开。」承诺早已在场（三生成物头部 status 行 + 生成物禁手改声明 + 归档闸机判），履约载体缺失：归档闸把 devkit/skillpack 的 status 钉死为「待Owner人审」且 flippedBy=不适用——它是永久性声明而非审批流起点态，「这版生成物被人看过并认可过」没有任何机判或人审载体；且 mcp-manifest 根本不在人审头体系内，三类不一致（design-human-review-gate §1 现状盘点）。

核心冲突（design §2.2）：`--check` 的语义是「入库副本 = 现场再生结果，逐字节一致」，而传统审批流的产出是对文件内容的修改——若人审以「改生成物」为产出，逐字节比对必红，人审与防陈旧在同一个字节串上互斥。解法枢纽：**人审的产出不是修订，而是审定批注旁档；内容修正诉求一律回流真源**（本体内容错走提案池 MR，装配/生成器错走票；修完真源 → 再生 → 生成物自然更新）——现行契约（生成物头部「禁手改，可再生」+ 归档闸 flippedBy 原文「人审结论经提案/票据落定后随再生更新」）早已规定了旁档回流解法，缺的只是旁档本体。

## 裁决

§6 决策点七点全按推荐，Owner 2026-09-20 拍板（design §8 原文照录）：

1. **承载形态 = A（审记旁档状态机 + 哈希锚定）**，吸收 C 的防伪面（verify 现算 sha256 与审记锚定哈希比对）；不引 GPG/外部签名设施。B（Git MR 制）不采用，理由是结构性的：单人仓 MR 是自审自合；派生物禁手改 ⇒ MR 的 diff 恒等于再生结果，MR 审阅退化为「看 diff 有没有」——这正是 `--check` 已经机判的事，不产生新信息；本体的内容人审已在提案池 MR 流程里，生成物再开 MR 会造成两个 MR 面同审一份内容（design §2.3）。
2. **manifest 档位 = 纳入登记为免审级**（消除三类不一致，「有意不审」显式化——免审 ≠ 免除声明，仍要在归档登记表登记档位）。
3. **三生成物初始档位 = manifest 免审 / skillpkg 首审+变更审 / devkit 全审**（design §3.2 落位；判档依据 = §3.3 四判据组合规则：再生确定性/消费方/输入面/diff 可读性，新产物接入按同一张表随票判档）。
4. **审记落点 = `exports/reviews/`**，归档闸登记 review-record 产物类（照票 37 给 devkit/skillpack 登记的先例，反向把审记本身入闸）。
5. **失效严格度 = 哈希不一致即自动失效，零宽限**（宁多审一次不放过）；审记丢失/损坏按「待人审」处理，不做重建——审记可以缺，不可以编（design §3.4 #2）。
6. **打回强制留痕 = 当场生成提案/票**（信号路由分道：本体内容错→业务错道提案池，装配/生成器错→工程错道票），不允许只记审记意见悬着——人审闸由此成为信号路由表的一个信号源（与元循环探针同位），而非独立流程孤岛（design §4 #3）。
7. **裁决落 ADR 0003**（本文件；推翻条件句式复用 ADR 0002）。

## 权衡

- 得：与 `--check` 防陈旧零张力（旁档不碰生成物本体）、与归档闸 status 契约零冲突（不动 status 字段）；哈希锚定把 C 的防伪力嫁接进 A 的低摩擦骨架，且复用 `--check` 的既有哲学——`--check` 判「入库=可再生」，哈希锚定判「已审=就是这一版」，两处比对同构、维护心智一套；打回强制路由杜绝打回悬在审记意见里。
- 失：人审是节奏性动作（发布/收官时点），不进每提交硬闸——机判四闸才是每提交闸，两者节奏混排会把流水线卡死在等人（design §5 不做 4）；单人范围下防的是「遗忘/错认版本」，不防「他人篡改」，B 的防伪与分工价值要到多人协作才出现（届时重开选型，见下）。

## 生效范围与推翻条件

- 生效范围：三生成物（exports/devkit/、exports/skillpkg/、exports/mcp/ capability manifest）与未来一切 exports 产物（新产物随生成器票按 design §3.3 四判据判档并随票登记归档表）。机判面 = tools/review_gate.py verify（哈希锚定失效判定）+ 归档闸 review-record 类 + 登记表 reviewTier 档位字段；档位承载在归档登记表，闸不重复判档。真源面的人审（本体内容变更诉求，提案池 MR）不在本裁决范围内——两面人审审的对象与问题不同，形态不必统一（design §4）。
- 推翻条件：承载前提失灵（审记旁档+哈希锚定被 Owner 复核证伪——实跑中不能可靠区分「审过的版本」与「再生后的版本」，或 verify 误报/漏报持续出现），则重议本裁决——考虑回退状态标记或改选型 B/C；**转为多人协作（PRD 决策 1 单人前提失效）时重开选型 B（Git MR 制）**——多人时 MR 的防伪与分工价值才出现（design §6 #1）。个别产物档位翻转（如免审级在下游炸出内容错→升档走票，工程错道）走信号路由处理，不推翻本裁决本身（design §3.4 #1）。
