## 1. 背景：本项目是什么、为什么现在提 DDD

- **All-agent = 企业语义中台 + 建造/运行一体化平台**：本体仓（Git+YAML）为唯一真源，多输入（需求/数据库/源代码/文档）多输出（应用包/Skill/MCP/分析报告/运行时语义服务）。形态：skill+脚本，不建代码系统。
- 建造方法 `sdd-flow2`：skill=深模块（卡/边界/依赖/输入输出契约/出厂集测试/归档）；约定不落闸等于没有。
- **本项目自身不用 DDD（有意为之）**：产物全是版本化文件，没有交易热路径；规则在提交时被闸拦截（等价于 DDD 聚合方法的运行时拦截），Git commit 等价于事务。本体仓反而是 DDD"统一语言"的最强落地物。
- **但平台"建出来的项目"可能是交易型系统**——那时需要 DDD。平台只锁死"说法"（本体+语义服务+闸），放开"走法"（架构风格）。ddd-modeler 就是给"走法=DDD"的备选项。

## 2. 已对齐的 DDD 共识（浓缩版，规划时直接引用，勿重新论证）

### 2.1 DDD vs 传统

- 传统：先建表→再写逻辑，规则散在 Service（贫血模型），任何代码可改任何字段。
- DDD：先建领域模型（聚合，数据+行为）→ 规则唯一一份封在聚合方法 → 表是聚合的持久化投影，仓储负责存取。
- 一句话：**传统="表→逻辑"；DDD="模型→逻辑→表"**。

### 2.2 聚合与事务边界

- "聚合改数据" = 改数据只有一个入口（聚合根的方法），仓储把整个聚合一次性存盘。
- **一个事务只改一个聚合**。聚合内多表（订单+订单行）= 一个事务整体保存；跨聚合（订单/库存/积分）= 拆成多个事务 + 事件串联，最终一致。
- 画圈判据：必须"同时成立、同时改、不能出现中间态"的数据放一个聚合；聚合宁小勿大。

### 2.3 聚合间通信（DDD 的 runtime 骨架）

- 领域事件是聚合间唯一合法通道；载荷引用本体词条 ID，不用裸列名。
- 三件套对策：**保序靠按聚合 ID 分区；并发靠版本号乐观锁；重复靠事件 ID+inbox 幂等去重**。
- 跨聚合长流程用 Saga 编排器显式写流程+补偿动作，不用事件链"接力赛"。

### 2.4 部署三档

| 阶段 | 事件总线 | 适用 |
|---|---|---|
| 起步 | 进程内发布订阅 | 模块化单体，丢事件可重试 |
| 认真做 | Outbox 落表+轮询投递 | 单体，事件不能丢（90% 项目够用） |
| 拆分后 | Kafka 等 MQ | 微服务/大流量；换投递通道，架构不变 |

- 一个域 ≠ 必须一个微服务：DDD 给边界（缝），部署形态另行决策；单体→微服务是"沿缝切开"。

### 2.5 与数据库范式的关系

- DDD 不破坏范式：表照样 3NF；DDD 有时**加表**（事件表/读模型），不改范式。
- 纪律差别：聚合边界内的表只允许一个代码库写；跨聚合不 JOIN；聚合整体存取。
- 表结构层面 DDD 与传统可共库中立，但**混写会绕过纪律**——"谁的表谁写"要落闸。

### 2.6 本体 × DDD 分工 + 语义层

- **本体管"说法"**（概念/属性/关系/口径，机器可读的词典），**DDD 管"运转"**（状态机/不变量/事务）。本体是宪法，DDD 是机器，数据库是仓库。
- 语义层不是表结构、也不是 DB 与后端之间的转换中间件——它是**词条定义+到物理表映射的元数据**，落成仓内 YAML（可选加薄查询服务）。
- 建设三档：①定义文件进仓（YAML：ID/定义/口径/映射/负责人）→ ②薄语义查询服务 → ③指标平台。
- 灵魂纪律：下游引用词条 ID 不引用列名；一个口径一个归属；改表≠改语义（改语义走评审）。
- 本仓 `ontology/` + `semantic-service` 就是该模式的最小实例。

### 2.7 调用链条各角色上场时机（防"语义层当中间件"误用）

| 时机 | 语义层上场方式 | 频率 |
|---|---|---|
| 开发时 | 查词条定契约（字段名/事件载荷/枚举引用词条 ID） | 每功能一次 |
| CI 闸 | 校验映射/禁用词/必填词条 | 每次提交 |
| 事件消费 | 词条 ID 校验（本地缓存本体快照） | 每条事件（查内存） |
| 读/报表 | 词条→SQL 解析 | 每次查询 |
| **交易热路径** | **不上场** | — |

### 2.8 AI 时代的成本账（为什么现在建这个 skill 值）

- 人肉时代 DDD 贵在学习曲线+仪式感代码量；AI 时代这两项暴跌，**剩下的成本只有运行时复杂度**（事件最终一致/Saga 补偿，AI 也消灭不掉）。
- 收益反而变大：**聚合卡 = 自带边界的上下文包**（聚合卡+不变量清单+出厂测试 = AI 改动的全部 world）；贫血长链 = 上下文黑洞。
- 结论修正：复杂交易系统从"可选"变"强烈建议"；简单系统仍然别用（排查事件/Saga 的成本 AI 一样贵）；中间地带核心域用 DDD、支撑域保持简单。
- **ddd-modeler 产的聚合卡+不变量+事件表，就是喂给 AI 的最佳工单格式**——这是"有利于后期 AI 维护"的真正形态。

### 2.9 可维护性承诺（验收时对 Owner 说的话）

- 规则只有一份家（聚合方法+词条口径），引用关系机器可查（impact-analyzer 沿 ref 反查）。
- 变更分级：小改（聚合几行+一条不变量测试+映射一行）很轻；中改（换口径）走词条评审+影响面清单；大改（新概念/新域）才走全流程。**重流程只被大变更触发**。
- 成本曲线：这套前期重、每次变更成本近似恒定；传统前期快、后期文档腐烂陡增。
- 对齐苦力（同步词条/重生成聚合卡/影响分析/补出厂集）= AI 的活，人只裁决。

## 3. 提案主体：三件套

### 3.1 ddd-modeler skill

流水线位置：

```
requirement-explorer（需求→草案）
      ↓
onto-modeler（草案→本体模型）        ← 词典已就位
      ↓
【ddd-modeler】（本体模型→战术设计）  ← 新增
      ↓
sdd-flow / F9 应用生成器（→代码系统）
```

深模块开卡表（初稿，规划 agent 可细化）：

| 项 | 内容 |
|---|---|
| 输入 | 某域的本体（模型文件+glossary）+ 需求草案中的行为/规则清单 |
| 输出 | ①聚合设计卡（聚合根/实体/值对象/不变量清单）②领域事件表（事件名/载荷词条 ID 引用）③聚合↔表映射 ④仓储边界声明 |
| 依赖 | onto-modeler 产物（无词条不许建模） |
| 边界 | 只产设计草案进仓走 MR，不做代码生成（那是 sdd-flow/F9 的事）；写意图走提案池 |
| 触发 | 选配：不是每个项目都路由进来（见 §5） |

设计件建议格式：聚合卡落成 YAML（机器可闸），放 `specs/` 或独立 `design/` 目录——规划 agent 定夺并与既有 specs 纪律对齐。

### 3.2 tools/ddd_check 闸（schema_check 同款风格）

检查项初稿：

1. 跨聚合引用必须是 ID，不得内嵌对方属性（防 JOIN 暗桩）。
2. 聚合字段/事件载荷必须能解析到本体词条 ID（术语对齐；词条悬空=红灯）。
3. 不变量清单非空，每条可指到聚合方法（防"贫血回潮"）。
4. 事件载荷词条版本对齐。
5. 表映射在位：聚合↔表映射中的表/列在映射文件中可解析（防映射腐烂）。
6. 归档纪律：按仓内 archive_check 既有规范接入。

### 3.3 fixtures 第八套出厂集

- 样本：一个最小订单域（本体输入 → 期望的聚合卡输出）+ 若干故意违规样本（跨聚合内嵌、词条悬空、不变量清单为空、映射断链），闸该红的红该绿的绿。
- 参考既有七套（schema_check/graph_index/onto-modeler/db-reverse/semantic-service/impact-analyzer/proposal-pool）的目录与验收形态。

## 4. 与 sdd-flow 全家的咬合 + 三处不重合

咬合（DDD 插在设计阶段一格，产物直接喂下游）：

```
PRD → 模块划分(深模块) → 【ddd-modeler 出聚合卡】 → 拆票 → TDD(按不变量写红灯) → CI 闸
```

- 聚合 = 深模块的标准像（窄接口深实现，"冰山模块"/NDD）；贫血模型 = 教科书级浅模块。
- 不变量清单 = TDD 的红灯用例来源；领域事件表 = 输入输出契约；边界纪律 = 闸。

三处不重合（规划时别把话说满）：

1. 深模块论"信息隐藏"，聚合论"一致性边界"——聚合做烂了照样是浅模块。
2. TDD 测行为，DDD 重语义——语义对齐只能靠词条闸。
3. SDD/深模块架构中立，DDD 自带运行时承诺（事件/最终一致）——这部分是 DDD 额外引入的复杂度，不是 sdd-flow 的要求。

## 5. 选配判断（什么项目路由到 ddd-modeler）

| 项目特征 | 判断 |
|---|---|
| 有状态机/不变量要守 | DDD |
| 规则多且持续增长，系统要活好几年 | DDD |
| 多领域多团队，边界是痛 | DDD |
| 读多写少、规则薄（报表/工具/CRUD/MCP） | 传统分层 |
| 一次性脚本/原型 | 都不上 |

核心判据：**"改一条规则要动几个地方"的风险有多大**。本仓当前的产物（应用包/Skill/MCP/查询治理型）大多不触发选配；交易型系统才路由进来。

## 6. 术语表

本对话造词：

| 词 | 含义 |
|---|---|
| 冰山模块 | 深模块的象形说法：水面窄接口、水下深实现 |
| NDD（Narrow-Deep Design） | 深模块的三字缩写，与 DDD/TDD/SDD 同族："这个类很 NDD" |
| 口小膛深 / 窄门深院 | 冰山模块的备选说法 |

DDD 核心词（对话中已对齐的定义）：聚合/聚合根（一致性边界，改数据唯一入口）、实体、值对象、不变量、领域事件（聚合间唯一合法通道）、仓储（聚合↔表映射的存取器）、限界上下文（语言边界）、统一语言（=本体词条）、Saga（跨聚合流程编排+补偿）、Outbox（事务内落事件表再异步投递）、幂等 inbox（事件去重）。

## 7. 开放问题（规划 agent 必须逐条给结论，标"待 Owner 确认"）

1. **第一版闸闸什么**：建议第一期只闸"设计卡 YAML"（聚合卡/事件表/映射），代码级闸（跨聚合 JOIN、裸 UPDATE）后置到有真实被建项目时再定——避免空转。待 Owner 拍板。
2. **Saga/事件运行时是否纳入第一期**：建议第一期只到"聚合+事件表定义"（设计件），运行时件（Outbox 实现/MQ 接线）由被建项目按需建，skill 不预建。待 Owner 拍板。
3. **词条 ID 的机检格式**：ddd_check 要解析词条 ID，需确认 `ontology/` 现行 ID 命名规范与引用语法（是否已有 check_citations 可复用）。
4. **设计件落盘位置**：`specs/` 既有纪律是否容纳聚合卡，还是另立目录；需与归档闸（archive_check）对齐。
5. **与 F9 应用生成器的接口**：F9 消费聚合卡还是本体？建议聚合卡作为可选增强输入，第一期不改 F9。
6. **批次排序**：DDD 线 vs L5 首次全量实战 vs A 线（提案裁决/第二域）的先后，Owner 裁决。
7. **票拆法建议**（起点，非定案）：① 设计件规范+ddd-modeler 骨架（含开卡表定稿）→ ② tools/ddd_check + 四闸接线 → ③ fixtures 第八套出厂集 → ④ 文档对齐（PRD/AGENTS/CONTEXT 词条）+ 端到端走查。每票自包含交接包、一票一提交、四闸全绿。
